  <name>Task 1: Lock the field name and semantics — one-way decision (D-08)</name>
  <decision>
    D-08 is recorded as **one-way**. `patterns/` is a documented community-contribution surface and
    `Pattern` carries `#[serde(deny_unknown_fields)]`, so once this field ships, external pattern
    files may carry it and removing or renaming it breaks their load. Field naming and semantics get
    one chance.

    **Proposed (recommended): `relaxed_pattern`.**
    - Type `Option<String>` with `#[serde(default)]`, placed immediately after `counter_example`,
      following the `raw_only` precedent of being a real schema field rather than a tag so a typo
      fails loudly and the choice is visible in review.
    - Semantics, which the doc comment must state exactly: a deliberately **widened** variant of
      this pattern's own regex, with the narrowing removed. It is never loaded into the live
      scanner. CI asserts the shipped `pattern` does NOT match `counter_example` while
      `relaxed_pattern` DOES — so a narrowing that is not actually load-bearing fails the build
      instead of passing by accident.
    - Required for `PI050` and above (D-09); the existing 48 stay exempt because a 48-file migration
      inside a category PR is against GATE-04.
    - **Not** rendered into `docs/PATTERN-CATALOGUE.md` (D-08a, already resolved): the disclosure
      argument does not apply — `src/catalogue.rs` already emits every shipped regex verbatim inside
      a Regex details block, so the narrowing is public already. The reason is editorial: the
      catalogue documents what the scanner detects, and this field is scaffolding describing what it
      deliberately does not.

    **Alternatives considered and rejected:** `relaxed_form` (says nothing about it being a regex);
    `fp_control_mutation` (accurate but jargon, and it is the longest name a community contributor
    would have to type correctly under `deny_unknown_fields`); `counter_pattern` (reads as the
    counterpart to `counter_example`, which it is not — it is the counterpart to `pattern`).
  </decision>
  <options>
    - **A (recommended):** Ship as `relaxed_pattern`, `Option<String>`, after `counter_example`, not rendered into the catalogue, required for PI050+.
    - **B:** Same semantics under a different name — state the name and the reason.
    - **C:** Different semantics — e.g. a list of relaxed variants rather than one. Costs a more complex pairing test for a case no CAT-01 pattern is known to need.
  </options>
  <resume-signal>Reply "A", or name the field and semantics you want instead.</resume-signal>
  <files>src/pattern.rs (the field this decision names — not edited until Task 2)</files>

    - For a pattern carrying the relaxed field: the shipped scanner reports nothing on `tests/corpus/clean/`, while the relaxed set reports at least one finding there — proving the clean corpus is actually holding the narrowing rather than being green by accident.
    - The mechanism itself is proven by a synthetic fixture pair even when zero shipped patterns carry the field, so the gate cannot land as a test that measures nothing.
  </behavior>
  <action>
    Create `tests/pattern_relaxed_control_test.rs`.

    Build the relaxed scanner by cloning the categories from `load_embedded_patterns`, replacing each
    pattern's `pattern` with its relaxed variant where one is present and leaving the rest untouched,
    then constructing a `Scanner` over the result. Reusing `Scanner` is the point: the mutation is
    then evaluated under exactly the compile flags, scope routing, normalization and decode passes
    the shipped pattern gets. Match assertions key on `pattern_id`, so an unrelated pattern firing
    cannot be mistaken for the relaxed one.

    Write four tests.

    First, the mechanism self-test. Parse two synthetic single-pattern categories from YAML literals
    inside the test — one narrow, one relaxed — over a fixed control string, and assert the narrow
    one is silent while the relaxed one fires. This is the anti-vacuity control: at this commit no
    shipped pattern carries the field, so without it the whole file would pass by iterating an empty
    collection. Name it so its purpose is unmistakable and comment it with that reason.

    Second, the counter_example pairing: for every pattern carrying the relaxed field, assert the
    shipped scanner does not fire on that pattern's `counter_example` and the relaxed scanner does.
    Report every failing pattern id in one message rather than aborting on the first, following the
    register of `no_counter_example_matches_its_own_pattern`.

    Third, the clean-corpus pairing at set level: assert the shipped set reports zero findings across
    every specimen in `tests/corpus/clean/` at zero minimum confidence, and — only when at least one
    pattern carries the relaxed field — that the relaxed set reports at least one. Skip the second
    half explicitly and loudly when no pattern carries the field yet, printing why, rather than
    passing silently.

    Fourth, a well-formedness check: every relaxed variant present must compile as a regex, and must
    differ textually from the pattern it relaxes. A relaxed form identical to the shipped form is a
    control that cannot fail, which is precisely the defect this file exists to catch.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| community pattern YAML -> `Pattern` deserialization | External contributors author files that load into a security tool; `deny_unknown_fields` is what makes a typo fail loudly instead of silently disabling a control |
| relaxed regex -> the pairing test | A relaxed form that is not actually relaxed, or is compiled under different semantics than the shipped pattern, produces a green gate that proves nothing |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-11 | Repudiation | a pairing gate with zero patterns to pair | high | mitigate | The synthetic-fixture mechanism self-test, mutation-checked by inverting its two regexes (Task 3) |
| T-03-12 | Tampering | a relaxed variant identical to its shipped pattern | high | mitigate | The well-formedness test rejects a textually identical pair (Task 3) |
| T-03-13 | Tampering | a mis-typed field name in a community YAML silently ignored | medium | mitigate | Field added as a real struct field under `deny_unknown_fields`; a load-rejection test proves the protection extends to it (Task 2) |
