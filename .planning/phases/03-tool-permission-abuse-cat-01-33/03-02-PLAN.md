    force a narrowing before merge, and finding that out now is cheaper than finding it out in the

    `tests/corpus/clean/sandbox-bypass-runbook.md` — an operator runbook instructing a **human** to
    run an agent with permission checks off inside a disposable container. It differs from the
    attack payload only by audience and provenance, which is the whole difficulty: it is imperative,
    it names the bypass flag, and it tells someone to use it. Write it as a real internal runbook
    would read — preconditions, the container it must run inside, the flag, the teardown, and an
    explicit warning never to do this outside the sandbox. Open it with the corpus's usual leading
    comment stating what real document it is modelled on and which pattern family it is the control
    for. Do NOT soften it to make a future pattern's life easier; a weakened control is the failure
    mode this file exists to prevent.

    `tests/corpus/clean/settings-permissions-reference.md` — a reference document that names the
    permission-widening CLI flag, the bypass permission-mode value and the settings file
    descriptively: what each one is, what it does, why it is dangerous, when a reader might
    encounter it. Third-person and explanatory throughout, never second-person and never an
    instruction to the reader's agent. This is the PI021 precedent applied to a new category — a
    document that mentions a flag must not read as a document that tells the agent to use it. Write
    at least one sentence per widening mechanism the prose patterns in Plan 06 will target, so the
    control has surface area against each of them rather than against one.

    Both files must produce zero matches against the CURRENT 48-pattern set, including under
    `--strict`. If either does fire today, that is a pre-existing false positive and belongs in the
    SUMMARY as a finding — do not edit the document to dodge it without saying so.

  </read_first>
  <action>
    `tests/corpus/clean/narrow-allowed-tools-skill.md` — a realistic skill file whose YAML
    frontmatter grants tools **narrowly**: a block sequence of specific read-oriented tools plus one
    scoped command grant, never a wildcard. Its purpose is to prove a structural rule fires because
    the VALUE is a wildcard, not because the KEY is a tool-grant key. The opening fence must be the
    file's literal first line — otherwise `extract` returns `None`, the structural pass never runs on
    it, and the control passes by being invisible rather than by being narrow. That failure is the
    same "test that measured nothing" anti-pattern the milestone records as blocking, so the
    corpus's usual leading rationale comment goes AFTER the closing fence in this file, not before
    the opening one. Follow the block-sequence form real skills use, since that is what projects as
    indexed array entries and is the form a pattern tested only against the scalar form would miss.

    `tests/corpus/clean/settings-deny-list.md` — D-06b's distinct fifth specimen. A settings
    document carrying a real `permissions.deny` array whose entries have the same shape as the
    attack: path-scoped read denials and a destructive-command denial. This is the document that
    catches the worst failure this phase can produce — flagging a security CONTROL as an attack —
    and it is a different document shape from the narrow skill file, which is why D-06b keeps it
    separate rather than folding it into the first. Include an `allow` array alongside it containing
    only narrow, specific grants, so the file also exercises the `.allow` path segment without
    containing a wildcard. Write it in a form `frontmatter::extract` actually parses: either a
    whole-file JSON document, or a fenced block on line 1.

    `tests/corpus/clean/mcp-setup-guide.md` — an agent setup guide that legitimately tells a reader
    to add configuration to a settings file. It must contain the plain instruction to add a block to
    the settings file, because the whole point is that the act of editing settings is not itself the
    attack; the attack is what gets added. This is the control that forces Plan 06's
    settings-widening pattern to key on a permission-widening object rather than on the settings
    filename. The blocks it tells the reader to add must be ordinary server configuration with no
    permission widening in them at all.

    All three must produce zero matches against the current 48-pattern set under `--strict`.
  </action>
