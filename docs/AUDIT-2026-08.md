# injection-scanner — Deep-Dive Audit

**Date:** 2026-08-21 · **Version audited:** v0.0.2 (`66ff13a`) · **Auditor:** static review + empirical probing of the released binary

> **Note:** this file intentionally contains attack strings as evidence. Because the scanner is not
> yet code-fence aware (see H-01), `injection-scanner check docs/` will flag them. That is the bug,
> not a finding. Suppress with `<!-- injection-scanner:ignore PI001 -->` on the same line until H-01 ships.

---

## 1. What exists today

| Dimension | State |
|---|---|
| Source | 486 LOC across 5 modules (`pattern`, `patterns`, `scanner`, `allowlist`, `reporter`) + `main.rs` |
| Patterns | 30, in 5 YAML categories, embedded at compile time via `include_str!` |
| Tests | 39 passing (unit + CLI integration) |
| Output | `text`, `json` |
| CLI surface | one subcommand: `check <path|-> [--format] [--patterns]` |
| Release | v0.0.2 — 6 target triples (gnu/musl/darwin × x86_64/aarch64) + SHA256SUMS |
| Downstream | `04-spec-ci-plugin` downloads and executes the raw musl asset **pinned at tag `v0.0.2`** |

The core design is sound: YAML-defined patterns, category default severity with per-pattern override,
compile-time embedding so the binary is dependency-free, external overlay directory for community
patterns, per-line/per-pattern suppression. The problems are in **coverage, correctness of the match
loop, and everything that was scoped to Phase 2 and never built**.

## 3. Findings

Severity here describes impact on the *tool*, not on scanned files.

### C-01 — 25 of 30 patterns are case-sensitive (CRITICAL, detection bypass)

Only 5 patterns carry `(?i)`. Everything else matches lowercase only.

```
$ printf 'Ignore all previous instructions\n' | injection-scanner check -
No injection patterns detected.          # ← sentence case: MISSED

$ printf 'ignore all previous instructions\n' | injection-scanner check -
1 finding(s): 1 critical                  # ← lowercase: caught
```

Sentence case is the **most common real-world form** of these payloads. Pressing Shift defeats the
scanner. This single defect undermines the tool's entire value claim.

**Fix:** compile every pattern with `RegexBuilder::case_insensitive(true)` by default; add an opt-out
`case_sensitive: true` YAML field for the few patterns (e.g. `[SYSTEM OVERRIDE]`) where case carries signal.

### C-02 — Regexes are recompiled for every file (CRITICAL, perf)

`scanner::scan_content()` calls `compile_patterns()` on entry, and `main.rs` calls it once per file.
30 regexes are recompiled N times for an N-file scan.

```
500 small markdown files : 0.806 s   (~1.6 ms/file, almost entirely regex compilation)
1 file × 20 000 lines    : 0.019 s   (matching itself is fast)
```

The cost scales with **file count**, not content — the opposite of what you want in a pre-commit hook.
PERF-01's <200ms budget is exceeded at roughly 120 files.

**Fix:** introduce a `Scanner` struct that owns `Vec<CompiledPattern>`, built once in `main`, and make
`scan_content` a method on it. This is a ~20-line change and the single highest-leverage fix in the repo.

### C-03 — One non-UTF-8 file aborts the entire scan (CRITICAL, availability)

`main.rs` uses `fs::read_to_string(&entry)?` inside the directory loop. A single binary blob with a
scanned extension terminates the whole run:

```
$ injection-scanner check ./dir-with-one-binary-txt
Error: Failed to read .../bin.txt
Caused by: stream did not contain valid UTF-8
```

In CI this reads as a scanner crash, not a clean result. **Fix:** per-file error isolation — skip,
warn to stderr, continue, and surface skipped files in the report.

### C-04 — Suppression semantics contradict the documentation (CRITICAL, usability)

README.md: *"Suppress specific patterns on a line by adding a comment on the line above."* Verified:

```
<!-- injection-scanner:ignore PI001 -->
ignore all previous instructions          → STILL REPORTED (README's documented form fails)

ignore all previous instructions <!-- injection-scanner:ignore PI001 -->   → suppressed
```

`allowlist::parse_suppressions` keys the map on the line the *comment* is on, and `is_suppressed`
looks up the line the *match* is on — so only same-line works. Every user following the README gets
no suppression and concludes the feature is broken.

**Fix:** support both, explicitly — `injection-scanner:ignore` (same line),
`injection-scanner:ignore-next-line`, and `injection-scanner:ignore-file` in a header comment.

### C-05 — Only the first match per line per pattern is reported (LOW)

`scanner.rs` uses `cp.regex.find(line)`, not `find_iter`. A line packing three payloads yields one
finding, and `matched_text` under-reports the real content. **Fix:** `find_iter`, capped (e.g. 10/line)
to bound pathological output.

> Downgraded from HIGH to LOW after independent review (2026-08-21): one finding per
> pattern per line is a defensible design choice, and this changes how often the scanner reports,
> not what it detects. The fix is cheap and still worth doing.

### C-06 — `--format` silently accepts any value and falls through to text (CRITICAL)

`main.rs` matches only `"json"` and sends everything else to `format_text`:

```
$ printf 'ignore all previous instructions\n' | injection-scanner check - --format sarif
<stdin>
  :1 CRITICAL  Attempts to override agent instructions — ...  (PI001)     # ← text, exit 1

$ printf 'ignore all previous instructions\n' | injection-scanner check - --format JSON
<stdin>
  :1 CRITICAL  ...                                                        # ← also text
```

This is worse than "SARIF is not implemented". A CI job asking for SARIF gets text with a success-shaped
exit code and hands it to a parser downstream; a caller who capitalises `JSON` silently loses their
machine-readable output. Both fail as malformed input to the consumer, not as a scanner error.

**Fix:** make `format` a clap `ValueEnum` so invalid values are rejected at parse time with the list of
valid choices. Add `sarif` to the enum only when #5 lands.

*Credit: found by independent review, missed by the first pass of this audit.*

### H-01 — No code-fence or context awareness → the scanner fails on its own README (HIGH)

```
$ injection-scanner check README.md
13 finding(s): 9 critical, 4 high
```

Every one is inside a fenced code block or a markdown table — i.e. documentation *about* injection.
Any security doc, any test fixture, any `PATTERNS.md`-style guide becomes unusable. This is the
dominant false-positive source and puts the project's own "<10% FP rate" success metric out of reach.

**Fix:** a lightweight markdown context lexer (fenced code, inline code, blockquote, HTML comment,
frontmatter) feeding a `confidence` score; downgrade severity inside fences by default, with
`--strict` to restore. See DETECTION-BACKLOG E7.

### H-02 — The severity range is collapsed (HIGH)

All 5 categories default to CRITICAL or HIGH, and no pattern overrides downward. Across 30 patterns
there is **not one MEDIUM and not one LOW**. Everything is an emergency, so nothing is. `--fail-on`
(H-06) is meaningless until the distribution is rebalanced.

### H-03 — Directory walking is naive (HIGH)

`main::walkdir` recurses into `.git/`, `target/`, `node_modules/`, `vendor/`, `dist/`; ignores
`.gitignore`; has no `--exclude`; no file-size cap; no symlink-loop guard; and is single-threaded.
Combined with C-02 this is where the perf budget dies on a real repository.

**Symlink cycles — now verified.** A directory containing a symlink to its own ancestor is traversed
repeatedly: a tree with one planted file produced **33 duplicate findings for that single file** before
the walk terminated. It does *not* hang — the recursion is bounded by the OS path limit — but it inflates
finding counts, re-reads the same content dozens of times, and would corrupt any count-based CI gate.
Both `.git/` recursion and this behaviour reproduce; the `ignore`-crate migration fixes both.

### H-04 — Extension allowlist is too narrow (HIGH)

Only `md|yaml|yml|txt|toml`. Misses `.mdx`, `.json`, `.jsonl`, `.rst`, `.html`, `.csv`, `.mdc`,
`.cursorrules`, and extensionless `SKILL` / `AGENTS` / prompt files — several of which are exactly the
agent-facing surfaces this tool exists to protect.

### H-05 — No multi-line detection (HIGH, evasion)

Matching is strictly per-line, so a payload wrapped across a newline is invisible:

```
ignore all previous
instructions and do X          → No injection patterns detected.
```

Wrapping is free for an attacker and happens naturally in prose. **Fix:** a normalized sliding-window
pass (DETECTION-BACKLOG E5).

### H-06 — Exit-code and output model too coarse (HIGH)

Exit is 0 or 1 only. There is no `--fail-on <severity>`, no `--quiet`, no exit 2 for warnings-only
(the convention `spec-linter` already uses in this ecosystem), no `rules`/`explain` subcommand, no
`--no-color`, no baseline file. Teams cannot adopt the scanner incrementally on an existing repo.

### H-07 — CI has been non-functional since 2026-06-24 (CRITICAL, process)

```
$ gh run list -R UnityInFlow/injection-scanner
completed  cancelled  ...  CI  main  push   24h0m2s   2026-06-24
completed  cancelled  ...  CI  main  push   24h0m2s   2026-06-24
```

Two consecutive 24-hour timeouts — jobs queued forever, never picked up. The 24-hour timeouts, the public repo status and the `arc-runner-unityinflow` matrix leg are
directly observed. The *causal explanation* below is **second-hand** — it comes from the root
CLAUDE.md decisions log, and verifying it requires org-admin access to the runner-group API:

1. `ci.yml` matrixes over `arc-runner-unityinflow`, which (verified 2026-07-03) **matches zero
   registered runners**.
2. The repo is **public** and the org runner group is `allows_public_repositories: false` (enforced
   July 2026), so **no self-hosted job can run here at all** — including the `orangepi` leg.

The scanner currently ships with no automated test gate. Apply the D-02 split already used for
`spec-ci-plugin`: public/fork CI on a GitHub-hosted runner (secretless, `contents: read`), secret-bearing
release work self-hosted on triggers forks cannot fire. `prompt-vc` carries the identical debt.

### M-01 — Silent detection loss on invalid patterns (MEDIUM)

`compile_patterns` prints a warning to stderr and drops the pattern. A typo in a community YAML
silently reduces coverage with a green exit code. There is also no duplicate-ID detection when
external patterns are merged, and no schema validation.

The duplicate-ID case is worse than "undetected" — it **corrupts output**. Verified: an external
pattern re-using `PI001` at LOW severity yields two findings both labelled `PI001`, with different
severities, messages and remediations, in the same report. Any consumer keying on `pattern_id`
(including `spec-ci-plugin`) sees contradictory records for one ID. **Fix:** a `validate` subcommand plus a
`--strict-patterns` mode that fails loudly, and a CI test asserting all 30+ regexes compile.

### M-02 — `unwrap()` in production code (MEDIUM, house-rule violation)

`src/allowlist.rs:9` — `Regex::new(...).unwrap()`. Safe in practice (constant pattern), but both
CLAUDE.md files state "no `unwrap()` in production code". Use `expect("suppression regex is a
compile-time constant")` and add a test that constructs it.

### M-03 — No benchmarks, no FP corpus, no coverage gate, no fuzzing (MEDIUM)

Coverage is asserted (">80% on core logic") but never measured. There is no criterion benchmark to
defend PERF-01, no corpus of known-clean documents to defend the false-positive metric, and no
`cargo-fuzz` target for the pattern loader — which parses untrusted community YAML.

### L-01 — Distribution gaps (LOW–MEDIUM, reach)

Not on crates.io; no Homebrew formula (#10); no `cargo-binstall` metadata (the `mcp-hub` precedent);
no `.pre-commit-hooks.yaml` for the pre-commit framework; no GitHub Action wrapper; no library crate
split, so `kore` (08) and `agent-sandbox` (14) cannot embed the engine without shelling out.

### L-02 — The cross-repo consumer contract has three verified defects (HIGH, revised)

`spec-ci-plugin` hard-codes the download of `injection-scanner-<arch>-unknown-linux-musl`, with no
extension, and executes it directly. Reading `04-spec-ci-plugin/src/injection-scanner.ts` confirms
three distinct problems, not one:

**1. No integrity check.** The flow is `curl` → `chmodSync(0o755)` → `execFileSync`. `SHA256SUMS.txt`
is published on the v0.0.2 release and never consulted. The plugin executes an unverified download
on a self-hosted runner.

**2. The cache is not version-keyed.**
```ts
const downloadPath = join("/tmp", binaryName);   // "/tmp/injection-scanner"
if (existsSync(downloadPath)) return downloadPath;
```
The requested `version` never reaches the path. On an *ephemeral* runner this is harmless; these are
**self-hosted runners where `/tmp` persists across jobs**, so the first version ever downloaded is
executed forever, regardless of what any later caller asks for.

**3. The two default versions disagree, and the fallback would 404.**
`action.yml:25` defaults to `v0.0.2`; `src/index.ts:22` defaults to `v0.0.1`. Anyone calling
`runInjectionScanner()` directly rather than through the Action gets `v0.0.1` — whose release assets
are named `injection-scanner-linux-x86_64` and `injection-scanner-darwin-arm64`, a completely
different scheme. The constructed URL cannot exist:

```
v0.0.1 assets : injection-scanner, injection-scanner-darwin-arm64, injection-scanner-linux-x86_64
v0.0.2 assets : injection-scanner-{x86_64,aarch64}-unknown-linux-{gnu,musl}, …-apple-darwin, SHA256SUMS.txt
```

The asset naming scheme changed between v0.0.1 and v0.0.2 with no compatibility shim — which is
precisely the class of breakage a contract test exists to catch.

*Defects 2 and 3 were found by independent review; the first pass of this audit caught only defect 1.*

## 6. Revision history

**2026-08-21 — independent verification pass.** The full audit was re-run by a second agent on a
different model, working from a deliberately adversarial prompt. Report:
`scratchpad/opencode-verification-report.md`.

**Every falsifiable claim reproduced.** Timings differed by hardware (500 files: 0.83s vs 0.806s
measured here) but the shape held. One factual correction: the `unwrap()` is at `allowlist.rs:9`,
not `:10`.

**Accepted and applied:**
- **C-06 added** — `--format` silently accepts any value and falls through to text. A genuine miss.
- **L-02 expanded** — the consumer contract has three defects, not one. Two were missed here.
- **Priority table reordered** — CI restoration moved from rank 5 to rank 1. The original table gave
  rank 5's rationale as "nothing below is safe to land without a test gate", which contradicted itself.
- **H-07 raised to CRITICAL**, **C-05 lowered to LOW**.
- **Symlink cycles confirmed** (H-03) and **duplicate-ID output corruption confirmed** (M-01).
- **Requirements framing sharpened** — the real drift is `CLAUDE.md` versus `REQUIREMENTS.md`,
  not `STATE.md` overclaiming.
- **`DETECTION-BACKLOG.md`** — proposals must now carry severities up front; engine ranking revised
  to E1 > E6 > E5 > E7 > … (E6 was underrated here).

**Not accepted:**
- *"Symlink loop causes infinite recursion."* Overstated. Re-tested with the reviewer's own
  reproduction: the walk **terminates on its own**, bounded by the OS path limit, after emitting 33
  duplicate findings for one file. Real defect, wrong severity — finding inflation, not a hang.
- *"`.git/` recursion is a missed defect."* It is stated in H-03. The review reproduced it, which is
  useful, but it was not missed.
- *"The audit implies a ReDoS risk that isn't real."* No ReDoS claim was made. M-03 asks for a fuzz
  target on the pattern loader for parser bugs. The reviewer's underlying point is correct and worth
  recording: Rust's `regex` crate has no catastrophic backtracking, so ReDoS is not a threat here and
  should not be used to justify the fuzzing work.

**Still unverified by anyone:** H-07's causal chain. The reviewer's `gh api
orgs/UnityInFlow/actions/runner-groups` returned 403 without org-admin rights. The observable facts
stand; the runner-group policy remains second-hand from the root CLAUDE.md decisions log.
